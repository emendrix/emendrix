LEVEL 0

The claim the whole design is arranged around

One sentence, and everything below is a consequence of it.

EUR-Lex will show you the current text of a regulation but not what changed. emendrix subscribes to the EU's own publication feed, notices when an act you watch is amended, computes a provision-level delta between two consolidated versions, and writes a plain-English changelog into a git repository, where every sentence carries a citation that resolves.

The technical thesis The amending act already says what changed, and that part is parsing, not inference. The model's only job is to say what the difference means, constrained to the two texts in front of it.

That thesis buys a very specific division of labour, and the codebase enforces it mechanically rather than by convention. The model never decides whether something changed, which provisions are involved, or how to classify a change. It is handed two verbatim texts and a set of citation keys, and it may return sentences. Nothing else.

Enforced by import boundary

pydantic_ai may be imported only under explain/, plus the eval judge. langgraph only under graph/build.py. Network only in eu/http, eu/cache, eu/feed. A test greps for violations.

Enforced by the output type

The model returns Explanation: sentences plus citation keys. There is no URL field, no location field, no change-type field. A hijacked call has no slot to put a payload in.

Enforced by the clock rule

No wall-clock read inside diff, classification, corroboration, gating or rendering. Dates arrive as values from the CLI boundary. Two runs over the same inputs produce identical bytes.

Enforced by first-class states

ConsolidationPending, EnglishUnavailable, Disputed, ApplicabilityUnknown are values that flow to the output and get counted. Raising where one applies is a bug.

LEVEL 1

Building blocks: the sealed vocabulary

emendrix.core: pure typed values, with no I/O, no clock, no model, and no knowledge of EU law. Everything imports it; it imports nothing back.

Four ideas in core/ carry the whole system. If you understand these, every other module is an implementation of something already named here.

1 · A provision location is a string

AR 5 PA 1 ALN 1 PTA (bb), AN III. A path of (code, value) segments that round-trips through one canonical string, sorts deterministically, and answers containment: AR 5 contains AR 5 PA 1. That string is the identity: what changes are keyed by, what goes into sets, what appears in the JSON.

The grammar is positional, not lexical. At a segment boundary the next token is a code, and the token after it is that code's value unless it is itself a known code. Codes outside the vocabulary become UnknownCode and are counted, never rejected. The top-level segment is the unit of change (the article or the annex), and every headline metric is computed at that granularity.

core/location.py · core/location_codes.py

2 · A provision tree carries its text twice

Each ProvisionNode holds text, verbatim and never normalised, which is what the changelog quotes; and comparison_text, whitespace-collapsed, which is what the diff compares. The second is built by the parser at extraction time, with a separator at every element boundary.

This is not redundancy, and the repo records why: collapsing whitespace afterwards cannot put back an element boundary that extraction never emitted. On the REACH 2008 to 2009 pair, an extraction that lost those boundaries reported all 143 units as modified against 40 real ones.

core/provisions.py

3 · A Change is what the machinery computes, a Delta is the set of them

A Change carries its type (INSERTED / MODIFIED / DELETED / RENUMBERED / DEFERRED), the provision it lands on, verbatim before and after, the sub-coordinates that differ, the dates that moved, two separate clocks, and a SignalSet recording which of three independent signals saw it.

Validators do real work here: disputed is derived from the signals and a value contradicting them is rejected; an INSERTED change must have no before; a Delta refuses changes belonging to another act.

core/delta.py · core/changes.py

4 · Two clocks, kept apart

in_force comes from CELLAR's START_OF_VALIDITY and is a date. applies_from is a date only when it can be read deterministically from a date change in the act's own application article; otherwise it is ApplicabilityUnknown carrying a reason. Many unknowns is the correct outcome. The model is never asked to fill one in.

core/changes.py · diff/deferred.py

LEVEL 2

The loop, and what flows along each arrow

Seven stages. Six of them are pure functions over typed values; one of them talks to a model.

The most useful way to hold the system in your head is not the package list but the sequence of types. Each stage takes the previous stage's document and returns a strictly richer one. Nothing is dropped along the way: a change that cannot be fetched, cannot be explained, or that the signals disagree about still arrives at the end, carrying the reason.

Why a graph framework at all LangGraph is confined to one file, graph/build.py, and buys exactly three things: typed state threading (the state is a pydantic model, validated at every node boundary), a real cycle (gate back to explain, bounded at one), and resumable checkpoints. Everything else in graph/ is ordinary Python the tests call directly. No Send fan-out, no tools, no agent prebuilts, no interrupts: nothing in the graph decides anything, so there is nothing to interrupt for.
LEVEL 3

Inside each stage

The mechanisms, and the measured facts that shaped them.

WATCH: noticing an amendment exactly once

The watcher reads the Publications Office notification feed for one time window, matches entries against a watchlist of CELEX identifiers, and turns each hit into an AmendmentEvent. The hard part is not detection but not detecting twice.

There are two dedupe layers, because one is not enough. The first is by entry identity, which makes overlapping windows free: the poller can assume it died mid-run last time and simply re-scan. The second is by what the entry resolved to. CELLAR re-notified the AI Act's Digital Omnibus consolidation 46 times in one day, each under a fresh entry id. Without the second layer the watcher would announce the same amendment 46 times.

An entry the corpus has not consolidated yet does not fail. It becomes a persisted ConsolidationPending row, re-checked at the start of every poll before the window is walked, so an act whose text has finally arrived is reported even on a poll where the feed says nothing new. Measured lag between publication and a consolidated text: about ten days.

watch/poll.py · watch/state.py · eu/feed.py

FETCH: four possible answers, three of them states

Retrieval goes through CELLAR by content negotiation, always behind a disk cache. The design point is that a refusal is frequently a fact about the corpus, not an error:

consolidated <lang> fmx4        →  FormexPackage
   ↓ no such manifestation, and this is the act's first consolidation
the act as published in the OJ  →  FormexPackage, marked `fell_back`
   ↓ not available either, or the fallback does not apply
no text in that language        →  EnglishUnavailable
no structured text at all       →  StructuredTextUnavailable
version not consolidated yet    →  ConsolidationPending

Only 404 and 406 are read as "the document is not there". Every other non-200 (a 403, a 429, a challenge page) is the server refusing us, and turning that into EnglishUnavailable would persist a false claim about an act, so it raises loudly instead. The fallback to the original OJ text is deliberately narrow: it applies only when the requested version is the act's earliest consolidation, and the package records that it happened.

Verified reality, not assumption AKN4EU does not exist for these acts; the structured format is Formex 4. Provision-level ELI URIs 404, so citations render as EUR-Lex anchors. English is not guaranteed for a given consolidated version. XML is parsed only through eu/xml_.py using defusedxml, because every document here came off a socket and the stdlib parser expands internal entities.

DELTA: the structural diff

The diff works on top-level units only. It builds a dictionary of each version's roots keyed by canonical location and classifies every pairing. Units present in both with identical comparison text are counted as unchanged and never emitted. Units present in both with differing text are MODIFIED, unless the only difference is the dates they carry and the application date moved, in which case they refine to DEFERRED.

Below the unit, the diff also localises which sub-provisions differ (changed_within) and which machine-readable dates moved (dates_removed, dates_added). Those ride along as detail on the unit and never become units of their own, because every published metric is computed at article granularity and a second granularity would quietly change what the numbers mean.

CORROBORATE: three readings of the same question

This is the evaluation story, and it is the part of the design that most distinguishes the project. The question which provisions changed? is answered three independent ways:

  1. The structural diff, the primary shipped signal and the only one carrying actual text.
  2. CELLAR modification metadata, the annotations the Publications Office publishes per amendment. This is the reference label set and the source of the in_force clock. Role codes R, J and DEL are empirical: the authority tables publish no English labels.
  3. The instruction-prose parse, read from the amending act's own text ("in Article 5, paragraph 2 is replaced by the following"). A measured cross-check, never ground truth.

Each change ends up with a SignalSet of three verdicts. The crucial distinction is that UNAVAILABLE is silence, not dissent: a corpus publishing no metadata cannot disagree with anything.

How three verdicts become one outcome

Row three is the one worth dwelling on. A unit that the metadata names and the diff never saw is appended to the delta as a change with a location, a kind, no quotable text, and disputed = True. It is never dropped and never merged into a neighbour. Downstream, the explain stage recognises it as having nothing to explain and records that reason instead of calling a model.

The metadata is a reference, never an oracle On the REACH 2008 to 2009 transition the diff finds 40 units and the annotations name 9, because the corpus annotates a blanket amendment once and does not enumerate the thirty-odd places it lands. That produces 33 disputed changes, and it should: the disagreement is the finding, and the diff is the one that is right. Those are the figures tests/corroborate/test_eu_corroboration.py asserts; an earlier count of 8 and 32 came from a script that discarded a title the corpus names, and discarding it is forbidden.

EXPLAIN: the one place a model may speak

One bounded call per change: no tools, no memory, no multi-turn, no retrieval. What it is given is what prompt.py built; what it may return is what schema.py allows. Changes are independent, so a delta is explained concurrently under a semaphore, and asyncio.gather preserves order so result i is always change i.

The prompt opens with a header of deterministic facts, and it states the change type as a fact ("established by a structural diff, not by you") rather than asking for it: which provision this is, what type of change it is, which sub-provisions differ, which dates moved. The header is there so the model does not have to work any of it out, which means it is part of the evidence the writer had, and since 2026-08-09 the faithfulness judge and the human review worksheet are shown it too, with one boundary. Header facts ground a claim about which provisions changed; only the two texts ground a claim about what the words say. Those texts are printed inside fences, capped at 40 000 characters a side with the truncation visibly marked and the dropped count carried into the run statistics; the cap was 8 000 until 2026-08-09, sized when the pin was a cheaper model, and at 40 000 exactly one prompt of the pinned subset is still trimmed. It prints the offered citation keys. Then twelve binding rules: describe only the difference, no legal advice, at most three sentences, every sentence carries a key copied character for character, do not re-quote the texts, an honest "the only change is X" beats an inflated one, and, from a hand review of twenty shipped explanations on 2026-08-08, four more: nothing past the truncation marker, what the words changed rather than what the change legally accomplishes, no unverified claim about ordering or renumbering or counts, and the actor the text names is the actor named.

On prompt injection, honestly The fenced text is verbatim legislation from a remote endpoint. It can say anything, including something that reads as an instruction. The fence is not a constant it could forge: the delimiters are <<< and >>> followed by twelve characters of a sha256 of the texts about to be fenced, named one line above the first block, and a text cannot contain the digest of itself. What defends against the rest is that a hijacked call has nowhere to go: the output type has no URL field, no location field and no change-type field; citation keys are opaque tokens the caller minted, and the gate tests membership against the very object the prompt printed; the call is one bounded turn with no tools. The worst outcome is a bad sentence, which the faithfulness measurement catches and publishes.

Failure is a value. A provider error, a refusal or an exhausted schema-repair budget yields ExplanationUnavailable on that one change and the batch continues. Two exceptions propagate deliberately, a cassette miss and a corrupt cassette, because both are build faults rather than answers about a change. A corrupt one is the worse of the two, since it also shrinks the denominator every published rate is computed over.

Cassettes are how a model stage runs in CI at all. Every exchange is recorded to disk keyed by the model id, the system prompt, the user prompt and the schema version. In replay mode the provider agent is never even constructed, so no API key is read and no client exists to make a request. A schema change misses every existing cassette loudly instead of replaying a stale shape into a new validator.

GATE: why a citation cannot be hallucinated

This is the mechanism to understand if you only have time for one. The trick is that a citation is never something the model composes. The caller mints an opaque key for each provision the change may cite, and it decides which ones structurally, from the change type: an insertion has no "before" to cite, a deletion has no "after", so those keys simply do not exist in the offered set. The prompt prints that set. The gate then checks membership against the same object. There is no second construction of the offered set to drift from the first, which is the classic silent hole in a gate like this one.

The retry policy is one sentence long, and the code is arranged so it stays that way: check; on failure ask once more with the specific complaint; on a second failure quote the provision. The gate itself never calls a model. first_round hands back which changes want a revision, the orchestrator makes the call, and second_round rules on the answers, because a stage that both re-asked the model and decided whether the answer was acceptable would be the model marking its own homework.

Two properties are asserted as properties rather than examples: the gated delta is positionally aligned with the delta it came from, so input changes equal output changes always; and no ungrounded sentence ships, since every sentence in a settled delta either passed the check or was written by the gate as a verbatim quotation.

EMIT: the product claim, cashed

The claim is that your regulatory dependencies get the same review workflow as your code dependencies, and it is cashed here: a run ends as a commit in a repository somebody can diff, review in a pull request and blame.

<repo>/.emendrix-output                                this repository is one emendrix created
<repo>/eu/32017R0745/CHANGELOG.md                      newest entry first, rewritten in place
<repo>/eu/32017R0745/changes/02017R0745-20200424.json  the same event, structured

Three policies, each a decision rather than a detail. The repository is the user's: emendrix creates it if absent, commits into it, and never pushes. It must be a repository emendrix made: a path inside an existing working tree is refused, and a path that is a repository without the marker file is refused too. Both checks are needed, because after the first write the output repository legitimately has a .git of its own. Re-emitting is a no-op: rendered bytes are compared with what is on disk before anything is written, so an hourly cron produces one commit per amendment, not one per hour.

Four systematic disagreements the report names rather than tunes away

  1. Blanket amendments are annotated once. "…shall be replaced by … throughout the text" is one annotation and dozens of touched provisions. The diff finds them all; precision against the metadata collapses.
  2. Corrigenda are not amendments. A consolidation carrying only a corrigendum has no modification annotations at all, so every unit the diff finds scores zero precision. The MDR's first consolidation is exactly this case.
  3. The two location vocabularies spell some annexes differently. Legacy notices number four of REACH's annexes in Arabic where the Formex markup uses Roman, so the same annex appears as two units that neither signal shares.
  4. The instruction parse has two named blind spots, both counted as unread rather than approximated.
The rule these numbers are published under Never curate bad cases out of the corpus; never blur citation grounding into explanation quality; every metric carries what it does and does not mean. The model-layer figures are facts about one recording, made on 2026-08-09 against openrouter:anthropic/claude-sonnet-5 as the explainer and openrouter:openai/gpt-5.6-sol as the judge, and replayed offline ever since. A rate that gets better because the question changed says so in the same breath as the number: the faithfulness row rose from 0.800 to 0.850 across a change of evidence base and a raised character cap, so it is not the previous rate improved and the two are not comparable.

One provision, all seven stages

Medical Devices Regulation, 02017R0745-20170505 to 02017R0745-20200424, Article 34.

This transition is the COVID-era postponement of the MDR. The whole run touches nine provisions: three substantive, six date-only, none disputed. Follow Article 34 through.

WATCH

A feed entry names 02017R0745-20200424. It matches the watchlist, is not in the seen set, and the version inventory lists it with English available, so out comes an AmendmentEvent with previous_version = 02017R0745-20170505.

FETCH

Two Formex 4 packages come back through the disk cache and parse into two ProvisionTrees. Article 34 is a root node in both, each carrying verbatim text and a separately built comparison form.

DELTA

Keys match, comparison texts differ, so MODIFIED. Then the date reader finds the only difference is 25 March 2020 becoming 25 March 2021, so the type refines to DEFERRED and applies_from becomes a real date, 2021-03-25. Sub-localisation records AR 34 PA 1 ALN 1.

CORROBORATE

The metadata names the unit and supplies in_force = 2020-04-24. Signals agree, so disputed stays false.

EXPLAIN

Two keys are minted, one per side, and printed. The model returns one sentence, citing both keys it was handed. It offers no applicability note, and rule 7 asks for one only where the after text says when the provision applies; the date on the headline came from the diff, not from the model.

GATE

Both keys are in the offered set and both resolve in the fetched trees, so PASSED, first round, no retry. Had the model written an applicability note, the gate would also have checked it for containment in the after text as the model was shown it, and dropped and counted it if it were a paraphrase.

EMIT

The entry is rendered, the citation key becomes a EUR-Lex anchor, and the file is committed.

**DEFERRED · Art. 34 — Functionality of Eudamed** · applies from: 2021-03-25

*within* `AR 34 PA 1 ALN 1` *dates* -2020-03-25 +2021-03-25

The only change is the date by which the plan for implementing Eudamed's
functional specifications must allow the Commission to publish the notice
referred to in paragraph 3, which shifts from 25 March 2020 to 25 March 2021.
[Art. 34, v1] [Art. 34, v2]

*before* (`02017R0745-20170505`)   verbatim, quoted from the Change, not the model
*after*  (`02017R0745-20200424`)   verbatim, quoted from the Change, not the model

Note what the model contributed: one sentence. The change type, the provision, both dates, the sub-coordinate, the two clocks, the quoted texts and the resolvable links were all produced by deterministic Python before and after the call.
